# Setup

Run commands from the repository root. Examples use `192.0.2.10`, a reserved
documentation address: replace it with your camera's actual IPv4 address.
This guide does not require changing an NVR or camera overlay settings.

## Requirements

- Node.js 22 or newer and npm on the host.
- Docker Engine/Desktop or OrbStack, with Docker Compose v2 supporting
  `env_file.required` (Compose 2.24+).
- One to four ONVIF cameras reachable on their device-service HTTP port 80 and
  RTSP endpoints. The discovery CLI currently uses the default ONVIF port.
- A camera viewer account with permission to read profiles and streams. The
  fleet currently uses one shared camera login for all configured cameras.
- FFmpeg/ffprobe on the host only for `verify`, native runs, and media tests.
  On macOS: `brew install ffmpeg`. Docker includes its own FFmpeg and MediaMTX.

Docker deployment is recommended. Native runs also need MediaMTX 1.21.1 on PATH
and an FFmpeg build with the filters required by the project. Installation may
need a compiler toolchain if a dependency has no prebuilt binary for your system.

## 1. Install and Create Private Files

```sh
npm ci
npm run env:init
umask 077
cp -n proxy-config.example.json proxy-config.json
chmod 600 proxy-config.json .env
```

Initialization refuses to overwrite an existing `.env`. For an existing install,
skip that step and keep your working private configuration. The initializer
generates independent proxy and dashboard passwords without printing them; camera
credentials remain empty for you to fill. Edit private files in your editor,
never the committed examples, and keep a secure backup. No credential JSON files
are required. Create a viewer account in the camera's administration tools first;
the application does not create accounts or change their privileges.

In `proxy-config.json`, change the example camera's host, name, and OSD title.
Add up to three more entries if needed. Use unique IDs, IPv4 hosts, and ports:

| Entry order | Example ID | ONVIF port | RTSP port |
| --- | --- | --- | --- |
| 1 | camera-1 | 8080 | 8554 |
| 2 | camera-2 | 8081 | 8555 |
| 3 | camera-3 | 8082 | 8556 |
| 4 | camera-4 | 8083 | 8557 |

These port ranges match Compose. Changing them also requires updating its port
mappings. Names are display labels; IDs identify saved settings and recordings.
The `osd` object is optional. Its title supports letters, digits, spaces, periods,
underscores, and hyphens; set an appropriate IANA timezone such as `Etc/UTC`.

## 2. Configure the Environment

In private `.env`, fill every login field; leaving an empty key is not equivalent
to omitting it. For passwords containing `$` or `#`, use single-quoted dotenv
values so Compose and Node preserve them literally.

| Setting | Value |
| --- | --- |
| `CAMERA_USERNAME`, `CAMERA_PASSWORD` | An existing camera viewer login |
| `PROXY_USERNAME`, `PROXY_PASSWORD` | Generated by initialization for the proxy's RTSP/ONVIF services |
| `DASHBOARD_PASSWORD` | Generated by initialization; custom values must be 12-256 characters |
| `CAMERA_1_HOST` through `CAMERA_4_HOST` | Original camera IPv4 addresses, in config array order |
| `CAMERA_n_RTSP_HOST`, `CAMERA_n_RTSP_PORT` | Reachable RTSP address/port for each configured camera |
| `VIDEO_PROFILE`, `VIDEO_FPS` | Initial defaults, recommended `480p` and `10` |

Keep the generated passwords or replace them with independent password-manager
values. They must not be the camera administrator password. Camera and proxy
usernames/passwords must be nonempty single-line strings. Keep unused camera variables at their example
values or remove them; only entries present in the config are started.

For direct access, keep the **DIRECT LAN** block active and the **BRIDGE** block
commented. Set each active `CAMERA_n_RTSP_HOST` to the same address as its
`CAMERA_n_HOST`; port 554 is common but use the actual camera RTSP port.
Environment host values override the config by array position, not by camera ID.

Keep `ADVERTISE_HOST`, `WEB_BIND_ADDRESS`, and `STREAM_BIND_ADDRESS` at
`127.0.0.1` initially. `WEB_PORT` changes the Docker-published dashboard port;
the service still listens on port 3000 inside the container.

## 3. Discover Camera Profiles

With direct network access to the cameras, run:

```sh
node --env-file=.env src/cameras.js inspect --host 192.0.2.10
```

Repeat `--host` in the same invocation for every configured camera. Explicit hosts
are required unless `CAMERA_HOST` is set for a single-camera discovery run.
The command writes private `camera-inventory.json`, including device metadata and
credential-free RTSP profile URLs. Do not publish this inventory.

Optionally verify packet reception with host FFmpeg installed:

```sh
node --env-file=.env src/cameras.js verify --host 192.0.2.10
```

This rewrites the same inventory, so include all configured hosts again. Resolve
any per-camera error before proceeding. Hosts in the inventory must match the
original camera addresses, even when RTSP later travels through a bridge.
Do not invent profile URLs or copy another installation's inventory.

## 4. Start

```sh
docker compose config --quiet
docker compose up -d --build --wait --wait-timeout 120
```

Open http://localhost:3000 and sign in with `DASHBOARD_PASSWORD`. Check both
previews for every camera. Videos start muted; use native video volume controls
to listen when the camera supplies audio.

Private `.env`, `proxy-config.json`, and `camera-inventory.json` must exist before
Compose starts. Configuration/inventory bind mounts refuse to create missing
paths; credentials come only from the environment, with no file fallback.
Do not print `docker compose config` without `--quiet`: it exposes passwords.

## Remote Camera LAN via SSH

First discover the inventory on a machine that can reach camera ONVIF services.
The bridge forwards RTSP only; it does not make `inspect` or `verify` ONVIF
discovery work remotely. Transfer the inventory privately if needed.

Configure a key-authenticated SSH host alias, for example `camera-gateway`, in
your normal SSH config. That gateway must reach each camera's RTSP port. Verify
the gateway host key and SSH access yourself before starting the bridge.
No SSH private key or password belongs in this repository or `.env`.

1. Set `BRIDGE_SSH_HOST` to your alias and `OFFICE_RTSP_PORT` to the remote
   camera RTSP port (one shared port, usually 554).
2. Comment the complete DIRECT LAN block and uncomment the complete BRIDGE block.
   Keep the original `CAMERA_n_HOST` values; only connection endpoints change.
3. On Docker Desktop/OrbStack, keep bridge hosts as `host.docker.internal` and
   unique ports 15554-15557. Run `npm run bridge` in a separate host terminal.
4. Leave it running, then recreate the service while recording/replay is idle:

```sh
docker compose up -d --force-recreate --wait --wait-timeout 120
```

The bridge binds localhost only, uses RTSP/TCP, and stops on Ctrl+C. It has no
automatic reconnection supervisor. A Linux Docker host does not automatically
provide the same host-loopback access: `host-gateway` alone does not expose a
localhost-bound SSH forward. Use native execution with `127.0.0.1` bridge hosts
or a separately reviewed network arrangement; do not expose the forwards publicly.

## Native Execution

Install FFmpeg and MediaMTX 1.21.1, complete the same private setup and inventory,
and run `npm start`. It loads `.env` and starts the fleet on localhost:3000.
For bridge mode, use `127.0.0.1` instead of `host.docker.internal` as each RTSP
connection host. Docker bind variables do not configure native listening sockets.
Do not run native and Docker services on the same ports simultaneously.

Native settings default to `stream-settings.local.json`; recordings default to
`/tmp/onvif-recordings` or `RECORDING_DIRECTORY`. A native Linux install may need
`OSD_FONT_FILE` pointing to an installed font. Check font availability before use.

## Existing Installations

Preserve current environment credentials when upgrading; initialization is only
for a new `.env`. Older credential JSON files are not read by the application.
Before removing any local backup, verify its login is securely preserved. Keep
administrator credentials in a password manager, not the proxy environment.

Recreate the container after environment changes while capture/replay is idle.
The processed RTSP path is `/processed`, with ONVIF profile token `processed`.
Update external clients and refresh cached ONVIF profiles when upgrading from
an earlier stream-path scheme. No compatibility alias is provided.
